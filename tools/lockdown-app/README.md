# Lockdown app

A local web app for reviewing the RichView lockdown. It shows every item of a part, prefilled with the proposed answer, its IDs and sources, saves Daniel's accept, edit, reject or defer decisions to files in this repository, and renders the guide and the lockdown files for reading alongside. The file formats are defined in [`docs/lockdown/README.md`](../../docs/lockdown/README.md).

## Run

Node 20.11 or later; no dependencies and no build step.

```sh
node tools/lockdown-app/server.mjs                       # http://127.0.0.1:4790/
node tools/lockdown-app/server.mjs --port 4791           # another port
node tools/lockdown-app/server.mjs --root /path/to/repo   # another checkout (default: two levels up from the script)
```

The server binds to `127.0.0.1` only. To use it from another machine, forward the port over SSH, for example `ssh -L 4790:127.0.0.1:4790 claw-mini`, and open `http://localhost:4790/`. Run one server per checkout: writes are serialized inside one process, not across processes.

## Files

| Path | Access |
| --- | --- |
| `docs/lockdown/parts/*.json` | Read on every request, never written. A new, changed, half-written or invalid part file shows up within one poll (5 s) without a restart; an unreadable one is listed as unavailable with its parse error. |
| `docs/lockdown/answers/<part id>.json` | Written by the app only, atomically (temporary file and rename), one write at a time per file. An answers file that is not valid JSON is reported and never overwritten. |
| `docs/lockdown/answers/log.jsonl` | One line appended per answer change: `{at, partId, itemId, decision, text, note, action}`; `action` is `set` or `clear`, and `bulk: true` marks lines written as one batch ("accept all remaining", or a decision on selected rows). A clear logs `decision: null`. |
| `docs/guide/**/*.md`, `docs/lockdown/{README,GOALS,RULES,BOUNDARIES,EVIDENCE,DELIVERY,ids}.md` | Read-only Markdown for the Guide view, listed and read fresh on every request. The listing skips hidden entries and does not follow symlinked folders. A guide file may be a symlink only to another file inside `docs/guide`, `docs/guide` itself must not be a symlink, and a lockdown file must be a regular file at its own path. |
| `docs/lockdown/screenshots/`, `docs/guide/` | Images only, served under `/files/<repo path>`. |

The part id is the part's file name without `.json`. Each answer also stores `proposedHash`, a hash of the proposal it answered; when an agent later changes that proposal, the app marks the answer as changed and the export flags it as stale.

## Review flow

The start page (`#/`) says what the lockdown is and links to the Key decisions view with its progress ("Key decisions 3 of 104 answered"), then what accept, edit, reject and defer mean, what they mean on a card with options, the order to work in, the progress of every part, and links to the guide and the export. The order is: first the 19 cross-part contradiction cards in Part 08 (OPN-50 to OPN-68), which decide which part holds where parts disagree, so each is answered before or together with the cards it cites; then parts 01 and 02; then the rest. A link opens Part 08 at that group's heading, and the parts list marks 08, 01 and 02. The left rail lists Start here, Key decisions with its progress, the parts with their status, progress and key progress (`key 2 of 24`), then the Guide; the start page's parts list shows the same counts.

Every item may carry an `importance` (`key`, `important` or `detail`, defined in [`docs/lockdown/README.md`](../../docs/lockdown/README.md)). Cards and rows show it as a badge: Key stands out on the accent wash, Important and Detail are quiet text, and an item without one (or with any other value) is unrated and shows none. Within each group, items sort key first, then important, detail and unrated, otherwise in file order.

The Key decisions view (`#/key`, `#/key/<item>` for one card) lists every key item of every part on one page, grouped by part in the start page's order: Part 08's cross-part contradictions, then Parts 01 and 02, then the rest in part order (with Part 08's other key items under its own heading at the end). Its head counts the answered cards ("3 of 104 key decisions answered") and each part's heading counts its own ("1 of 19 answered"). Its filter bar has Importance (Key, or Key + important to widen it), Unanswered only, search, kind and component. It opens as rows; a row opens its full card in place with the same Accept, Edit, Reject, Defer, Choose, note and clear controls as in a part, and every answer goes through the same save, journal and retry code to its own part's answers file (selected rows from several parts are saved as one bulk write per part). Accept all remaining is not offered there. The view is built from every part, so a changed part file shows "Show the new version"; it reloads by itself while no card is rated.

A part shows its items grouped by `group`, in one of two layouts chosen per part with the Rows/Cards switch or `v` and remembered in `localStorage`. Parts with more than 40 items open as rows unless you chose otherwise. Its progress line adds the part's key count.

- Cards show each item in full: ID chips (click to copy), the component chip, kind, confidence, question, proposal, options, recommendation, conflict, sources and screenshots. Answered cards can be collapsed.
- Rows show one dense line per item: a checkbox, the item, entity and component IDs, confidence, decision state, a `decision` marker on decision items and an `N options` marker on items with options, the title, a one-line excerpt of the proposal (or of your edit or choice) and the four decision buttons. Clicking a row or pressing `o` opens the full card in place; several can be open at once. Select rows with their checkboxes (Shift-click selects a range), `x`, or "Select all shown" under the current filters, then accept, reject or defer them in one write from the bar at the bottom. Changing existing answers asks first and names edits whose text would be lost; rows hidden by a filter leave the selection.

Every answer button explains itself on hover (its `title`, also its `aria-description`): Accept keeps the proposal as written (on a card with a recommended option, takes that option; on a card that already holds an edit or choice, it says it would replace it), Edit is your own wording that saves as you type and replaces the proposal, Choose picks an option as your whole answer, Reject drops it so the rewrite does not build or follow it, Defer decides later, Note is a comment for the agents and not an answer, and Clear answer removes your decision. A card with options says above them: "Choose an option, or Accept takes the recommended one. Choosing is your whole answer." "How answering works" in the header, or `?`, opens a panel with the same explanations at the right edge (on screens 1360 px or wider the page makes room for it); `Esc`, `?` or Close closes it.

An answered item reads as done at a glance. Its badge names what it holds: Accepted, Your edit, Chosen: <option label>, Rejected or Deferred on a wash, while an open item shows a hollow ring and Open. An answered row's title and excerpt are muted and its other buttons fade until hovered. The card's save line says `Saved as your edit` or `Saved as your choice` with the time, so nothing needs accepting on top.

Accept, Edit, Reject and Defer save immediately, and an edit saves as you type. A note on a card with a decision saves as you type; a note on a card without one is kept in this browser and saved together with the decision. Clear answer removes a decision.

Nothing you change is lost when a save fails. Every change is written to a journal in this browser's `localStorage` (`lockdown.journal.v1`, keyed by part and item) before it is sent, and leaves the journal only when the server confirms it. A failed save shows Not saved with Retry on its card and is sent again automatically on the next poll that reaches the server (every 5 seconds while the tab is visible). Leaving a part, "Show the new version" and reloading or closing the tab keep the journal; opening the part puts its entries back into their cards. A line under the header counts the changes not saved and the notes kept in this browser, with a link to the first unsaved change, and closing or reloading the tab asks first while a change is not saved. An unsaved change is sent only while the server still holds the answer it was made on; if a newer answer was saved since (from another tab, device or writer), the card shows the conflict with "Use my unsaved change" and "Keep the saved answer" and nothing is overwritten. The journal belongs to the browser and the address: open the app at the same `http://localhost:<port>/` each time, since another port is another origin with its own journal.

Agents write answers only when Daniel gives them live and asks the agent to record them (allowed since 2026-10-26), and only through the answer API (`cli.mjs answer`, which refuses to replace an answer without `--force` and marks the note as dictated); they never edit `docs/lockdown/answers/` files. Otherwise they change proposals in `docs/lockdown/parts/` only. Above the items you can filter by importance (All items, Key, or Key + important, with counts), Unanswered only, topic, decision (Show), kind, component or text, and accept every remaining proposal after an inline confirmation. All filters combine; "Showing N of M", "Select all N shown" and decisions on selected rows cover only what they leave shown. The importance choice is remembered in `localStorage` (`richview-lockdown.importance` for every part, `richview-lockdown.importance.key` for the Key decisions view); the other filters last for the visit. Unanswered only is the quick form of Show: Unanswered, and the two stay in step. The topic filter lists the part's `group` headings with counts and appears when a part has more than one. The component filter appears when items name a component (parts 04a to 04d); clicking a component chip shows only that component's items, and clicking it again shows every item. Opening a hidden item from a link clears the filters for that visit and leaves the remembered importance as it was.

On a card with `options`, each option shows its label as wrapping text, its detail and a Choose button, and the option the recommendation names is marked recommended. Accept takes the recommended option (the proposal states it; when no option is recommended, Accept keeps the proposal as written). Choose picks another: it saves decision `edit` with the text `Chosen option: <label>.`, a blank line and the option's detail, and the card shows the option as your choice with its button pressed, the state as Chosen and the edit as "Your choice"; the row shows `Your choice: <label>`. Reject means none of the options and drops the proposal; Defer leaves it open. Accepting in bulk, with "Accept all remaining" or on selected rows (including `Shift+A`), skips items with options, and its confirmation says how many it skips and that each needs an explicit choice; accepting one such item on its own still works.

Keys work in both layouts: `j`/`k` move between items, `a`/`r`/`d` accept, reject or defer and move on (in rows this also closes an opened row), `e` edits, `n` writes a note, `u` clears, `v` switches rows and cards, `o` or `Enter` opens or closes a row, `x` selects it, `Shift+A`/`Shift+R`/`Shift+D` decide every selected row, `/` searches, `?` opens or closes How answering works, `Esc` closes it, leaves a text field or closes a row, and `Ctrl+Enter` saves an edit.

## CLI for agents

`cli.mjs` lets an agent run a live review with Daniel from the terminal: it reads cards through the HTTP API below, reads links from `docs/lockdown/map/map.json`, and writes answers only through `PUT` and `DELETE /api/answers`, never by editing files. Node 20 or later, no dependencies. `node tools/lockdown-app/cli.mjs --help` prints the whole usage.

```sh
node tools/lockdown-app/cli.mjs status                       # answered per part, key and cross-part cards, decisions
node tools/lockdown-app/cli.mjs next -n 5                    # next unanswered cards in review order
node tools/lockdown-app/cli.mjs show INT-25 --brief          # question, proposal, options, recommendation, conflict
node tools/lockdown-app/cli.mjs deps INT-04                  # decided by / decides / conflicts / depends / mentions
node tools/lockdown-app/cli.mjs ripple INT-04                # unanswered cards to recheck after INT-04's answer
node tools/lockdown-app/cli.mjs answer INT-03 --choose 2 --dictated "the second, it is shorter"
```

Every command prints compact text, or JSON with `--json`. The server defaults to `http://127.0.0.1:4790` (`--url` or `LOCKDOWN_URL`); the checkout defaults to the one holding the script (`--root` or `LOCKDOWN_ROOT`) and should be the server's root, since `deps` and `ripple` read its map. Both rebuild the map with `build-map.mjs` first when `map.json` is older than a part or answer file; a failed rebuild keeps the existing map with a warning. Review order is importance (key first), then the start page's order (Part 08's cross-part cards, Part 01, Part 02, the rest), then file order. Card links use `http://localhost:<port>/#/part/<part>/<item>`, the address the browser journal expects.

`answer` and `clear` are for recording what Daniel answers live in the review chat and asks the agent to record; otherwise the rule above stands and he answers in the app. `answer` refuses to replace an existing answer unless `--force` is given, and then prints the old answer first. `--choose` saves exactly what the Choose button saves (decision `edit`, text `Chosen option: <label>.`, a blank line and the option's detail). `--dictated "<quote>"` puts `Dictated by Daniel in the review chat on <date>: "<quote>". Recorded by the lockdown agent at his request.` in the note, followed by `--note` when given; without either, `--force` keeps the existing note. After saving it prints the answer and the card's ripple.

## Guide view

`#/guide/<repo path>[#<heading>]` renders a guide document or lockdown file with the same escaped Markdown renderer as the cards. A leading H1 becomes the page title, front matter is dropped, and long documents get a contents list. Headings get GitHub-style anchors, and the `§` beside a heading links to it. Relative links to other guide documents and lockdown files open inside the app; relative images under `docs/lockdown/screenshots/` or `docs/guide/` load through `/files/`, and other images become links. Fenced `mermaid` blocks show their source, wrapped. The rail and the open document follow the files on disk within one poll.

Links follow one rule everywhere. An item ID (`INT-`, `DEL-`, `ARC-`, `FEA-CH-`, `FEA-RP-`, `FEA-SF-`, `FEA-BR-`, `TYP-`, `STY-`, `PRF-` or `OPN-` and digits) that some part has links inside the app wherever it appears: summaries, questions, proposals, options, recommendations, conflicts, source labels and refs, guide pages and the start page. Following one opens its part, clears filters that would hide it, opens its row or expands its collapsed card, and scrolls to it (to its group's heading when it is the group's first card); Back returns to where you were. A repo path links to GitHub only where it exists: at `https://github.com/1vecera/richview/blob/b4db233/<path>` when the pinned commit has it, on the `lockdown/richview-20261021` branch when it is a file on disk under `docs/lockdown/`, `docs/guide/` or `tools/lockdown-app/`, and a folder to its tree. `origin/<branch>:<path>` links to that branch, `.github/…` and `.claude/…` keep their leading dot, and any other path renders as plain code. When git cannot list the pinned commit, or the server predates `/api/repo-paths`, paths link as before: by their top-level folder. `PR #N` goes to the pull request, `S27-N` and `DIR-N` to Linear, and old `richview-universe/richview-v3` URLs to the new repository. In Markdown, code spans that name a repo path (`crates/richview-core/src/lib.rs:1-9`) or an item become links; from a card, guide documents open in a new tab so the review keeps its place.

## HTTP API

| Method and path | Purpose |
| --- | --- |
| `GET /api/parts` | Parts in order: id, title, status, order, revision, item and answered counts, counts by decision, `importance` (`{key, important, detail, unrated}`, each `{itemCount, answeredCount}`), warnings, and the error for an unreadable file; `totals` sums them. |
| `GET /api/items?importance=key,important` | Items of every readable part with `partId` and `answer` merged in, in part order and then file order, limited to the listed levels (`key`, `important`, `detail`, `unrated`; omitted means every item; an unknown level is 400), plus `parts`: every part's id, title, status, order, revision and error. The Key decisions view reads it; against a server that predates it (404) the UI reads every part instead. |
| `GET /api/parts/:id` | The part with each item's `answer` merged in, plus answers whose item has left the part (`orphans`). |
| `PUT /api/answers/:partId/:itemId` | Body `{decision, text, note}`; `decision` is `accept`, `edit`, `reject` or `defer`, and `edit` needs `text`. |
| `POST /api/answers/:partId/bulk` | Body: an array of `{itemId, decision, text, note}`; all entries are saved or none. |
| `DELETE /api/answers/:partId/:itemId` | Clears the answer. |
| `GET /api/export.md` | Markdown digest of every part for agents: each item's final decision and text, its entity, its component as `Component: <ID> <title>`, titled from the part 03 card, and its importance on the `Kind:` line. `?part=<id>` limits it to one part. |
| `GET /api/docs` | Guide documents, then the lockdown files that exist: `path`, `section` (`guide` or `lockdown`), `title` from the first heading (the file name when there is none), `revision`, `size`, `updatedAt`. |
| `GET /api/docs/<repo path>` | The raw Markdown of one listed location (`text/markdown`), with its revision in `X-Doc-Revision`; anything else is 404. |
| `GET /api/index` | `{itemId: partId}` for every item of every readable part, built from the part files on each request; an ID in two parts maps to the earlier part. The UI links item IDs with it. |
| `GET /api/repo-paths` | `{commit, paths, lockdownPaths}`: `paths` from `git -C <root> ls-tree -r -z --full-tree --name-only b4db233`, run once and cached (empty when git fails), and `lockdownPaths`, the files on disk under `docs/lockdown`, `docs/guide` and `tools/lockdown-app`, listed fresh without hidden entries or linked folders. The UI links a repo path only when it is listed. |

Writes need `Content-Type: application/json`. Requests whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` (any port) are rejected to block DNS rebinding, and so are writes whose `Origin` header differs from the address the browser used.

## Tests

```sh
node --test tools/lockdown-app/test/server.test.mjs tools/lockdown-app/test/journal.test.mjs tools/lockdown-app/test/cli.test.mjs
node --test tools/lockdown-app/test/ui-journal.test.mjs tools/lockdown-app/test/ui-review.test.mjs   # headless Chromium, needs the repository's npm ci
```

The tests start the server on an ephemeral port against a temporary root. They cover listing, answer merging, PUT, bulk and DELETE persistence with the log, validation, Host and Origin checks, path traversal on `/files`, malformed part and answers files, changed proposals, the export with its component lines, the document endpoints (titles, ordering, live updates, refused paths, traversal and symlink escapes), the item index, and the repo paths: the lockdown folders listed fresh, an empty commit list without git, and the commit's files read once from a temporary git repository where a ref named `b4db233` stands in for the commit. `journal.test.mjs` covers the journal itself: intents kept until their own send is confirmed, notes before a decision, retry versus conflict against the saved answer's `updatedAt`, and broken storage. `ui-journal.test.mjs` drives the app in Chromium: a failed decision kept across a reload and saved automatically once the server answers, the close-tab warning, a note typed before deciding restored after a reload and saved with the decision, a failed edit kept across leaving the part, and a stale journal entry that never overwrites a newer saved answer. The server tests also cover importance: normalized values, per-part and total counts, `/api/items` with its levels and part list, and the export line. `ui-review.test.mjs` drives the review aids: the importance filter (key-first order, badges, counts, the remembered choice in another part, Select all shown and a bulk decision limited to what it shows), the topic filter with Unanswered only and the answered badges, the Key decisions view (start-page progress, the rail link, groups in the start page's order, a choice saved to its own part, a failed decision journaled under its part and retried, Unanswered only, widening to Key + important, the answer visible in the part, and `#/key/<item>`), and the answer help (tooltips with `aria-description` on every answer button, the options line, the replace warning on Accept, and the panel opened by the header button and `?`, closed by `Esc`). `cli.test.mjs` runs the CLI against a server on a temporary root with three parts and a map built by the real `build-map.mjs`: `show` in full and brief, `next` in review order with its filters, `list` and `search`, `deps` and `ripple` (including a map rebuilt after a part changes), `answer` with accept, edit, edit file, choose by label and index, and dictated notes, the refusal without `--force` and the replace with it, `clear`, and `status`.

# Hotfix lane

Daniel authorized this lane on 9 November 2026: “yes send to prod, do a hotfix lane thanks”. It checks one `dev` commit on top of the current `prod`; the ordinary full-release path and the separate production and deployment go still apply to their respective actions.

Run `node tools/rv-gate/rv-gate.mjs hotfix <dev-commit>` on the gate host. The source commit must be on `origin/dev`, have a recorded fast pass for its patch and exact tree, and cherry-pick cleanly onto `origin/prod`. The command cuts a frozen `candidate/<n>`, runs fast against that prod parent and the affected Chromium checks, including changed verification scripts and chart-control checks, and writes an immutable `hotfix-…` receipt. It retains the receipt's build and reports each step's time and any wait for the shared release build. A failed or incomplete run is not a passing receipt. These checks do not replace the later full run.

Before requesting Daniel's go, run `node tools/rv-gate/rv-gate.mjs report --from origin/prod --to candidate/<n>` and include the packet's verification scope in the go request. After inspecting the receipt and obtaining Daniel's go for this candidate, run `node tools/rv-gate/rv-gate.mjs merge-prod candidate/<n> --go "<Daniel's words and date>"`. The gate checks the candidate, prod parent, source patch, required steps and build descriptor again. It refuses a stale prod and records the go and merge as the hotfix lane.

Production now contains a cherry-picked commit with a different identity from the source on dev. The gate merges prod back into dev automatically when the merge keeps dev's exact tree; it records the result alongside the hotfix receipt. A conflict or changed tree stops the back-merge and tells the operator to mail the lead; prod has already moved. Run the normal full checks on the resulting dev tip before the next ordinary prod promotion.

The site deploy is a separate action. Once Daniel authorizes that deployment, run `node tools/rv-gate/deploy-site.mjs --receipt <hotfix-receipt-id> --go "<Daniel's deployment words and date>"`. The helper verifies the exact current prod and staged build, refuses changes to Worker code or migrations under `cloudflare/`, records the existing Worker version as a rollback target, deploys the pinned Worker, and records the live checks and deployment receipt. If a post-deploy check fails, inspect the receipt and rollback evidence; do not assume the deployed site was restored.

# RichView Publish: Git-managed publishing and RichView News

## Intent

Build the first complete, open-source RichView publishing product for a small intelligence or specialist news publisher. Turn a repository of RichView reports and dashboards into a coherent publication: an edited front page, sections, navigable archives, individual stories and dashboards, trusted reader access and an accountable editorial workflow. The ambition is the publishing experience and editorial control of a serious publication such as [FT.com](<http://FT.com>), scaled to a small team and hundreds of items, with Git and coding agents as the natural authoring and approval interface.

The product name is **RichView Publish** (the final correction from “RichView Publishing”). The public demonstration is **RichView News**, at [**https://news.richview.ai**](<https://news.richview.ai>), which Daniel can keep publishing to as the product develops. Keep the authoring name **Rich Markdown**. Deliver implementation, product UI, examples and documentation in English. This is a separate product effort within the existing RichView monorepo, alongside Reports, Dashboards and Charts.

## Output format

Deliver a working implementation in the existing monorepo, a focused PR, reproducible deployment configuration, a maintained example content repository or tracked content directory, a live RichView News deployment, and end-to-end documentation under `docs/`. Retain a public-safe product brief as `tasks/richview-publish.md` in the implementation branch; omit private host paths, internal coordination details and execution routing from public artifacts. The completed product state is **delivered and verified**, beyond a plan, mockup, local preview or created PR.

**Publication and configuration.** Provide an editorial front page with masthead, navigation and deliberately selected lead stories; category/section pages; report and dashboard pages; useful browse/search/archive navigation; and support for static pages such as About. Support stable IDs/slugs, titles, summaries, authors/bylines, sections/tags, cover assets, publication/update dates, explicit draft/published/hidden state, audience, corrections and link-preserving updates. Keep the ordinary publication-wide layout, navigation, sections, theme and page composition configurable in at most **one site YAML file**. Existing per-report Rich Markdown, assets, data and optional styling YAML remain together in their established report folders; do not reinterpret the one-YAML preference as a ban on those files. Ship at least two genuinely distinct built-in editorial layouts selectable through that site configuration, not a new YAML programming language.

**Git-to-live loop.** A tracked content repository is canonical for publication content and ordinary editorial configuration. An author or agent adds or updates a report/dashboard, opens a PR, receives validation and a protected preview, gains the required approval, and merges to the configured publication branch; CI then builds and publishes the change online. Provide a clear status from source commit to build to live release. Correctly update affected front-page/section listings, links, search and feeds as well as the changed item, including deletion, rename and audience changes. Prefer dependency-aware incremental work where justified, but a correct bounded full build is acceptable for v1; this is a build/deployment problem, not React reconciliation. Demonstrate hundreds of representative fixture items without committing heavy generated outputs or making unsupported scale claims.

Build once into an identifiable immutable release and activate it coherently. A failed or superseded build must not replace the last good release; an older job finishing late must not overwrite a newer publication. Make rollback and recovery repeatable, and preserve the ability to rebuild from pinned source and toolchain. Separate canonical authored files from generated artifacts, large assets and runtime secrets. Document the actual trigger, preview, approval, build and hosting mechanisms selected from the existing environment.

**Reports and dashboards.** Render real RichView reports with working charts, assets, themes and existing interactions. Publish a real dashboard through the current dashboard artifact/runtime contract, with a clear distinction between a published snapshot and a live-data dashboard. Preserve provenance, freshness and access rules; no data or service credentials belong in the public browser. Integrate the existing dashboard work through a narrow supported boundary rather than rebuilding its voice/chat/semantic engine. A dashboard page must show a working dashboard, not merely a placeholder link. Private local saves from another task do not become public merely because this platform exists.

**Reader access and editorial control.** Support both an external publication and an internal publication using the same product, with explicit per-item audience where useful. External readers may browse intentionally public content; internal or restricted content requires authenticated membership/entitlement. Delegate identity, login and sessions to a proven existing provider or standards-based integration; do not build passwords, password recovery or a new identity service. Keep provider configuration replaceable and document one working deployment.

Use this initial role model, refining names only if existing contracts require it:

| Role | Required behavior |
| -- | -- |
| Reader | Browse the content permitted for the authenticated audience, with no editorial writes. |
| Editor | Create/edit drafts, metadata, section placement and permitted content; preview and submit changes for review; urgently hide content within their scope. Cannot grant roles or approve their own restricted publication action. |
| Super editor | Review/approve/publish, restore hidden items, curate front-page/layout settings and administer editorial roles and scopes through the supported integration. |

A small browser editorial surface must make quick source/text/metadata edits, adjustments and hiding practical. Ordinary edits create Git commits/PRs against the inspected revision, with actor attribution and conflict handling; never silently overwrite a concurrent Git/browser edit or keep an unexplained second content truth. Show draft, pending review, approved, building, live, hidden and failed states accurately. Separate reader identity from trusted repository write credentials and restrict the editorial bridge to the intended repository, paths and actions.

Urgent hide must immediately make the hosted content unavailable through supported delivery routes even if a build is slow or fails. If this needs a small runtime access/revocation layer, make it explicit, audited and reconciled back to Git. A stale deployment, rollback or later merge cannot silently undo an active hide. Define and demonstrate the precise hide/restore behavior, including direct URLs, old hosted release links, assets and cached responses. This withdraws hosted access; it cannot recall copies already downloaded by readers.

**Quality of the publication.** Aim for the hierarchy and craft of a small serious newsroom: convincing typography, a strong masthead, deliberate story ordering, readable article measures, meaningful image treatment and restrained analytical charts. Avoid a generic SaaS dashboard, a wall of identical cards or a thin reskin of the current marketing homepage. Give the editor predictable layout choices while retaining accessible mobile reading, keyboard navigation and legible chart behavior. Include appropriate titles/social metadata, canonical URLs, sitemap and RSS for public material; exclude drafts and restricted material from public search, feeds and metadata. The reference to [FT.com](<http://FT.com>) concerns product completeness and editorial quality, not copying its branding, content or paid subscription business.

**Demonstration and documentation.** RichView News should have enough clearly labelled, safe example material to exercise a front page, multiple sections, several reports, a functioning dashboard and continuing publication. Reuse suitable already-public RichView material when possible; synthetic examples must be labelled and factual stories retain their sources and dates. Also provide a real authenticated internal-mode demonstration without exposing internal data publicly.

Document the complete source-to-live operator journey, local setup, configuration schema/example, content contracts, provider setup, role mapping, PR/editor workflows, secrets, deployment, recovery, rollback and known limits. Include a concise architecture diagram and explain the ecosystem: Rich Markdown is the authored format; Charts is the rendering capability; Reports and Dashboards are publishable experiences; Publish is the publication/editorial/access/deployment layer; Server is existing hosting/runtime functionality to reuse and potentially absorb later; the VS Code integration remains an authoring surface. Describe the migration boundary without deleting Server or breaking current clients simply to rename it.

Retain concrete evidence against the deployed commit: live URLs and release/build identifiers; a Git/PR-driven addition and correction appearing online; an editor-created change returning to Git; restricted-reader and role-denial behavior; urgent hide and authorized restore; safe failed-build and rollback behavior; real report/dashboard interaction; and representative mobile/desktop output. Show that a newcomer can follow the documented setup and publish another item without a private undocumented manual step. Report what was independently exercised versus inherited or unverified. Do not mark completion from a successful build alone.

**Explicitly deferred.** Record, but do not implement in this first version, curated daily/periodic editions that combine multiple articles into one composed page; newsletter packaging/delivery; a crafted e-paper/print edition with editorially fixed composition; and a full RichView WYSIWYG editor. Preserve suitable IDs and content boundaries so these remain possible without building speculative infrastructure. Billing/paywall payments, ad tech, comments, CRM, enterprise multi-tenancy and a generic CMS extension marketplace are not required by the [FT.com](<http://FT.com>) analogy.

## What to maximize

* A complete, repeatable publishing loop: an agent or small editorial team can go from authored code to approved, discoverable, correctly protected live content and back to an auditable correction.
* Exceptional editorial presentation and ease of operation: one understandable site configuration, real RichView content, clear controls and a demo Daniel can use continuously.
* Small, reusable open-source architecture: reuse current RichView capabilities and ordinary Git/CI/identity infrastructure, with a documented path from the existing Server rather than a parallel platform.

## Hard constraints

* Git remains canonical for authored content and ordinary publishing configuration. All platform source stays in the existing monorepo under its compatible open-source licensing; no forked chart/report engine, bespoke identity system or hidden database-only editorial workflow. Runtime authorization/revocation state and secrets are explicit exceptions, not content storage replacements.
* Access control must protect the actual content and data, not just menus. Private/draft material, rendered artifacts, assets, search indexes, previews and old release routes must not be exposed through public URLs or a public source repository; untrusted PR builds receive no production write secrets. Keep private host/history/credential information out of public documentation.
* Authorization covers publication of RichView News at [news.richview.ai](<http://news.richview.ai>) using existing authorized infrastructure and safe example content, including the narrowly required domain setup when access exists. Preserve repository protections and concurrent work. It does not authorize new spending, publication of private reports/dashboard saves, unrelated merges or deployments, deletion of the existing Server, or sending newsletters/messages to an audience. If required access is unavailable, report the unresolved action and keep the delivery incomplete.

## Soft constraints

* Prefer the current monorepo architecture, hosting, identity and CI capabilities after inspecting them; avoid a framework rewrite or new services where existing ones suffice.
* Keep the publication useful at hundreds of reports with simple deterministic builds; prioritize correct dependency invalidation, repeatability and recovery before optimizing build speed.
* Use a small source/metadata editor and curated layouts now; reserve full visual authoring and editions for their separately recorded future scope.
